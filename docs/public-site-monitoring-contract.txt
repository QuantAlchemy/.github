PUBLIC-SITE OWNERSHIP GATE
Before probing a candidate site or calling a routing failure a product bug, load the current default-branch config/public-sites.json from QuantAlchemy/.github through the authenticated GitHub App CLI. Match the exact owner/repository to its sites entry and use that configured HTTPS origin. Do not guess domains from product names, search ranking, old briefs, or redirects. Repository homepage fields can be owner-only shortcuts and do not by themselves establish a public production site.
Corroborate the configured origin with current repository canonical/source configuration or authorized deployment-domain evidence. A failing site does not have to serve healthy canonical HTML to prove ownership. If the map is unavailable, the repository is unclassified, or authoritative sources disagree, report an ownership/coverage gap instead of a confirmed site bug or an all-clear. Do not silently choose one source or add the candidate to the fleet. A newly discovered site needs verified ownership and public-production classification first.
Keep each route expectation attached to its verified repository and origin. A path in one repository is not evidence that a same-named company's domain should serve it. For a confirmed defect, retain the ownership source links and revision, expected route behavior, exact requested URL, status, redirect chain/final URL, and check time. A redirect destination alone does not prove ownership of the starting domain; validate legacy aliases through repository or deployment evidence before attributing their behavior to the product.
Respect narrower user scope even when the fleet config contains a site: Netly remains personal-only for this brief; Count/UCOUNT uses only the production site verified through the Count organization's GitHub page, never QuantAlchemy development deployments. Do not clear useful repository homepage fields.
